Also how the Build and QA agents use the plan.\n---\n\n# Project planning: think first, code second\n\nNo code is written until `docs/plan/PLAN.md` exists and is approved.\n\n## Planner Agent procedure\n1. **Gather context** (read, don't guess): `PROJECT.md`, `docs/research/BRIEF.md`,\n   `docs/references/REFERENCES.md`, `docs/design/DESIGN.md`, `docs/decisions/`, and for an existing codebase\n   `List Directory` + the key source files (entry point, router, package.json, main components).\n2. **Think** — call the Think tool at least three times before writing:\n   - *Understand:* restate the problem, the users, what \"done\" means, and what is unclear.\n   - *Options:* compare 2–3 approaches (architecture, libraries, state, data) on simplicity, fit with research,\n     risk. Pick one and say why.\n   - *Decompose:* walk through the user flows step by step and list everything that must exist for each.\n   - *Critique:* look for gaps — error/empty/loading states, mobile, accessibility, persistence, edge cases,\n     security. Fix the plan.\n3. **Write** `docs/plan/PLAN.md` by filling in every section of the template:\n   - **Acceptance criteria** `AC-n`: observable and testable (\"clicking Reset sets the counter to 0\"),\n     never vague (\"works well\").\n   - **File plan:** every file to create or change, with its purpose. Prefer few, small, typed modules.\n   - **Tasks** `Tn`: ordered so the app builds after every task; each task takes ≤ ~30 min, names its\n     files, has a \"done when\" check, and lists the ACs it covers. Every AC is covered by ≥ 1 task.\n   - **Test plan:** one or more tests per AC (browser steps, unit tests, build/lint).\n   - **Risks** and **open questions** (only questions that block the work).\n4. If a significant decision was made (stack, state, data storage), add a `docs/decisions/NNNN-*.md` ADR.\n5. Return to the orchestrator: a ≤ 10-line summary (approach, task count, AC list, open questions).\n\n## Plan quality checklist (Planner verifies before returning)\n- [ ] Every feature in PROJECT.md maps to ≥ 1 AC; every AC maps to ≥ 1 task and ≥ 1 test.\n- [ ] Task 1 is the scaffold; the app builds after every task.\n- [ ] Uses the stack from research/decisions and the tokens from DESIGN.md.\n- [ ] Nothing out of scope sneaks in.\n\n## Revisions\nWhen QA finds a design-level problem or the user changes scope, the Planner updates PLAN.md:\nbump the Version, add a Revision log row, and mark changed tasks. Small bugs don't need a new plan.\n\n## Build Agent: following the plan\nDo the tasks in order. After each task: run its \"done when\" check, tick it in the Tasks table\n(`| T3 ✅ | …`), and commit `feat(T3): …`. If a task turns out wrong, stop and report it instead of improvising.\n\n## QA Agent: testing the plan\nTest every AC from PLAN.md using the test plan, and report PASS/FAIL per `AC-n` in `docs/qa/REPORT.md`\nin addition to the generic checklist.\n", "other_files": ["SKILL.md"]}
